# Spec 05 — The critic (Tier 2)

**Zone B, evolvable.** This is the Red Queen mechanism, restructured for a domain where
evaluation costs GPU seconds rather than LLM tokens.

Build this last. It is worth nothing on top of an untrustworthy oracle, and it is the
first thing to cut if time runs out — a documented design with an honest "not implemented"
scores better under Feasibility than a half-working one that inflates the numbers.

## What it is

```python
class Critic:
    epoch: int
    def score(self, source: str, shape: Shape, dev: DeviceProfile) -> CriticScore
```

`CriticScore`: `p_compiles`, `p_correct`, `pred_speedup_band: (lo, hi)`.

## What it is for

Skip GPU evaluation on predicted-hopeless candidates. With a compile-failure rate of
68–78% in comparable spaces, even a mediocre compile-failure predictor pays for itself
immediately. This is the cheap stage of an evaluation cascade — AlphaEvolve's hand-written
version of the same idea — with the difference that the cheap stage is learned and the
promotion rule is disciplined.

It is **not** a replacement for measurement. Nothing enters the ledger as a fact on the
critic's say-so. A gated candidate is recorded as gated, with the critic's epoch and score,
so the gate's own error rate is measurable after the fact.

## Implementation

Start with the cheapest thing that could work, and only escalate if it pays:

1. **Rules** — a static analysis pass over the source. Shared memory over budget, tile
   larger than the sequence, `BLOCK_N > HEAD_DIM`, obvious sync omissions. Free, and
   catches a real fraction of compile failures.
2. **LLM-as-critic** — a prompted model given the source plus the last N failures of that
   family with diagnostics. No training. Epoch-frozen prompt and model, which is what
   makes "promotion" meaningful.
3. **A small learned model** on features from the ledger — only if 1 and 2 do not pay.

The critic's own code and prompt live in `ratchet/critic/` and are what the meta-level
mutates between epochs.

## Epochs and promotion

**Freeze within an epoch.** The critic does not change while candidates are being scored.
This keeps the scoring stationary within an epoch, which is the whole reason the epoch
structure exists.

**Promote only at checkpoints**, on a schedule with exponentially increasing spacing
(e.g. after 64, 128, 256, 512 evaluations) so the amortized cost of a transition stays
linear in the budget.

**The promotion rule.** A challenger replaces the incumbent only when its ε-quantile
lower bound on the anchor exceeds the incumbent's:

```python
BB_eps(c) = beta.ppf(eps, 1 + successes_on_anchor(c), 1 + failures_on_anchor(c))
promote = BB_eps(challenger) > BB_eps(incumbent)     # ties favour the incumbent
```

Ties to the incumbent damps churn. The ε-quantile means a challenger must win with
statistical margin, not by lucky sampling. Use ε = 0.1 to start.

**A "success" on the anchor** is a correct prediction: the critic said gate and the
candidate would have failed, or said pass and it passed. Weight false negatives (gating a
kernel that would have been good) more heavily than false positives — a false positive
costs one GPU run, a false negative costs a discovery.

## The anchor — the part that must not be got wrong

The anchor is a **held-out slice of the ledger**, plus hand-seeded known-bad kernels.

Three non-negotiable properties:

**1. Held out by `candidate_id`, never by row.** A candidate's measurements on different
shapes are not independent samples. Split on the candidate, so a candidate's own rows
cannot appear on both sides.

**2. Generated by an oracle the critic cannot reach.** This is the failure mode that would
sink the whole design. The kernel domain makes anchor labels free — every candidate ever
benchmarked yields a ground-truth tuple, so the anchor is large, domain-matched and
continuously refreshed, and RQGM's stated first limitation ("evaluator quality is only as
good as its anchor") binds far less here than in its own domains. But that same cheapness
is exactly what makes the circular-anchor trap easy to walk into: **if the loop can edit
the harness that generates the labels, the promotion rule protects nothing.** Hence the
oracle's immutability, checksum manifest, and separate process. Those are not hygiene;
they are what makes this component meaningful.

**3. Includes known-bad kernels with known failure modes.** Seed by hand in
`oracle/known_bad/`, before the critic exists:
- one that returns its input unchanged (passes on all-positive inputs, fails on negated)
- one with a subtly wrong scale factor (`1/d` instead of `1/√d`)
- one correct only at a single benchmarked shape
- one that silently replaces NaN with zero
- one with a race condition that passes at low occupancy

A lenient critic must be **actively penalised**, not merely unrewarded. Without these, a
critic that says "pass" to everything scores well on an anchor made only of successes.

## What the critic must never touch

- **The tolerance.** `REL_TOL` and `ABS_TOL` are locked constants outside the evolvable
  workspace. If the critic could move them and the objective rewards passing, the loop
  will loosen them. This is the single most dangerous co-evolution axis and it is closed
  by construction.
- **The shape matrix.** Given by the competition. Evolving tasks is a different literature
  (POET, PAIRED) with a different anti-collapse mechanism, and RQGM has no analogue.
- **Any ledger measurement.** Critic epochs invalidate *predictions*. The `critic` block
  of a row is recomputable; nothing else in the row is.

## The adversarial input pool — build this before the critic

Cheaper, lower risk, and the highest-value co-evolution axis available here.

After each epoch, sweep the current best kernel over a wider input space than the
correctness suite covers, and collect every input where it **passed the harness but
disagreed with the reference**: denormals, NaN/Inf, non-contiguous strides, ragged tails,
extreme dynamic ranges that expose accumulation order. Append those permanently to the
correctness suite.

This is the direct analogue of RQGM's §5.4 adversarial pool, which corrected an evaluator
that over-accepted. A kernel harness over-accepts for exactly the same structural reason:
the tests were too weak. The pool converts that from a static problem into a search
problem.

Note honestly in the report that, as in RQGM, this correction is *designed in response to a
known failure class* rather than discovered by the loop. The mechanism gives you a place to
put such corrections; it does not invent them.

## Acceptance

1. On held-out data, false-negative rate on good kernels below a stated bound (start 5%).
2. `candidates_pruned × mean_eval_cost > critic_overhead`. **If the critic cannot pay for
   itself, report that and turn it off.** That is a legitimate negative result and more
   interesting than a marginal positive one.
3. All five known-bad kernels are scored as likely-to-fail by the promoted critic.
4. A critic epoch transition changes no `status`, `correctness` or `timing` field in any
   existing ledger row.
5. The gate's realized error rate is computable from the ledger after the fact, because
   gated candidates are recorded rather than dropped.

## Honest framing for the report

The evidence that a learned critic helps in *this* domain is thinner than the framing
suggests. RQGM's strong results are in paper review and proof grading — domains where
ground truth is fuzzy and a learned judge has room to add signal. Its coding result, the
one closest to ours, is **+3 tasks on n=166**, inside binomial noise. The generalization
from "learned judges help where judgment is subjective" to "learned judges help where you
have a compiler and a clock" is precisely the inference its own data supports least.

So: prototype on a bounded GPU-hour budget, measure whether it pays, and say either way.
